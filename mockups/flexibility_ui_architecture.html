Architecture · Flexibility UI

The screen has three states, and only one of them is the dashboard.

Today the model is empty, and an empty dashboard is not a dashboard — it is seventeen cards all saying “not measured”. Each state gets designed as its own screen with its own single job, rather than treating empty as a degraded version of full.

The root mistake

The screen was designed for the populated state and the empty state was allowed to fall out of it. But empty is where he actually is, it will be where he is for weeks, and it is the only state with an obvious single action. It deserves the most design attention, not the least.

Why there is nothing else here
The 22 yoga depth-ratings from 05 Aug are kept in full, and feed nothing. They answer “how far did I get and how much did I feel” — neither of the two things this model measures. Read them ›

Two cards instead of seventeen. The skills and rungs are not rendered at all in this state — a list of thirteen unmeasured things is a progress bar at zero, and it belongs inside the assessment flow where it can fill up, not on the dashboard where it just sits. The epistemology moves to a small secondary card; it is a good answer to a question nobody has asked yet.

State 2 — Capture. One test per screen.

13 tests × up to 3 measures × left/right is up to 78 numbers. As one form that is unusable and will be abandoned halfway; as one test per screen it is 13 short steps. It must be resumable, because 40 minutes is long enough to be interrupted and a half-finished assessment that vanishes will never be attempted twice.

Skip — no bench available

The lock is the loudest thing on the screen, above the setup and above the fields, because an unlocked joint is the failure that broke this model twice. Void is a deliberate control rather than a silent bad number. Skip is first-class — several tests need a bench or a wall, and a skipped rung reports honestly as unmeasured while a guessed one poisons a ladder.

Two gates the flow has to enforce

Cold. Asked once at the start, and recorded on the assessment. A warm reading measures the viscoelastic effect that is gone in hours, so a warm session is not comparable with a cold one and must be labelled, not silently mixed in.

Frozen constants. Three tests need a length measured once and reused forever — acromion-to-styloid, shin length, the traced foot outline. Session 1 captures them; every later session displays them read-only. Letting them drift silently re-scales the history.

State 3 — Populated. One answer at the top.

The original ask was “come to conclusions on where to focus in my training.” So the screen leads with a single rung, not four skill scores — and the model already computes which one, because a rung that limits three ladders is higher leverage than one limiting a single ladder.

Skills carry a goal mark on the track so “is 62 good” is answerable without reading a number. A skill on a partial ladder is visually distinct and labelled an upper bound, because it cannot be compared with a complete one. Rungs collapse by default — they are the diagnosis, and the diagnosis is already named at the top.

One output that falls out of the model for free

“limits 2 of 4 skills” is not a new metric — it is a count of how many ladders a rung is currently lowest on. lumbar sits on all four ladders, so if it is ever the limiter it is unambiguously the highest-leverage thing to train, and the screen can say so without any new measurement.

What I would build, in order

  1. The empty state. Two cards and a real button. Small, and it is the state he is actually in.
  2. The capture flow. 13 steps, resumable, lock shown loudest, void and skip as first-class controls, cold gate and frozen constants at session 1. This is the bulk of the work and nothing else matters until it exists.
  3. Persistence. ASSESSMENTS is an in-repo constant today. Readings need a real store — a Sheets tab matching the existing pattern, or the local datastore.
  4. The populated state. Cannot be tested against real data until 1–3 exist, so it is built last and against a fixture.
  5. The window. flexibility_window() exists and nothing calls it. It needs the training log and the rest-day intent flag first.
Still unresolved, and it blocks the window

The app offers yoga on rest days — the slot this model calls worst for adaptation. A restorative flow there is fine; a training session is not, and nothing in the code distinguishes them. Until a session carries an intent flag, the window cannot be shown without either being wrong or contradicting the button next to it.
